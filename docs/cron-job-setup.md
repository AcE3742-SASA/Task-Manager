# cron-job.org 예약 알림 설정

v1.5.0은 앱과 푸시 API를 Vercel에 두고, cron-job.org가 `POST /api/notify`를 5분마다 호출하는 구성이다. 호출 빈도와 별개로 알림은 사용자가 선택한 KST 정각과 마감 임박 시간대를 기준으로 보낸다. 기존 GitHub 예약은 새 연결을 확인할 때까지 유지한다.

2026-09-19 v1.5.0 운영 배포와 발송 없는 인증 연결 점검을 완료했다. cron-job.org 작업은 5분 간격으로 활성화했고 최초 알림 처리 시각은 KST 03:00이다. 실제 자동 실행, 기존 GitHub 예약 해제와 iPhone 수신 확인 상태는 마지막 기록란을 따른다.

## 서비스 제약과 키 관리

cron-job.org의 기본 제한은 응답 30초와 64 KB다. 정시 실행을 보장하지 않으며 연속 실패가 누적되면 자동 중지될 수 있다. 실패, 복구와 자동 중지 이메일 알림을 켠다. 공식 FAQ는 25회 초과 연속 실패를 중지 예로 든다. [공식 FAQ](https://cron-job.org/en/faq/)

같은 FAQ는 HTTPS 인증서를 검증하지 않는다고 명시한다. 공개 REST 설정에도 인증서 검증을 켜는 항목은 확인되지 않았다. 따라서 HTTPS 주소를 사용해도 cron-job.org가 연결하는 상대 서버의 신원을 제대로 확인한다고 볼 수 없다. 이것은 채택한 서비스의 제약이다.

cron-job.org에는 새 `CRON_JOB_SECRET`만 등록하고 Firebase 서비스 계정, VAPID 비밀키, 기존 GitHub 키를 주지 않는다. API는 이 키로 대상 UID, 본문이나 과거 발송 시각을 지정하게 하지 않으며 예약된 작업의 실행만 허용한다. 응답에는 합계와 상태만 넣는다. 전용 키는 노출 시 피해 범위와 교체 범위를 줄일 뿐, 인증서 미검증 위험을 없애지 않는다.

키는 로컬에서 생성해 Vercel 환경변수 화면과 cron-job.org 작업 설정에 직접 등록한다. 채팅, URL, 코드, 로그에 붙이지 않는다. cron-job.org 계정을 API로 관리하는 별도 API 키와 우리 알림 API의 `CRON_JOB_SECRET`은 다른 용도다. 콘솔에서 설정하면 cron-job.org 관리 API 키는 필요 없다.

## 1. 배포 전에 준비

1. 최종 코드의 단위 테스트, 타입 검사와 빌드를 통과시킨다. 합성 데이터에서 반복 호출, 부분 실패, 전송 후 기록 실패와 시간 경계를 확인한다.
2. 테스트용 Firebase 프로젝트와 Vercel 환경에서 로그인, 테스트 알림과 예약 알림을 확인한다. 실제 계정의 과제를 테스트에 사용하지 않는다.
3. Vercel Production에 별도의 `CRON_JOB_SECRET`을 등록한다. 기존 `CRON_SECRET`은 GitHub 수동 복구를 위해 유지한다. 두 키에 `VITE_` 접두사를 붙이지 않는다.
4. 기존 GitHub 발송이 진행 중인지 확인하고 완료된 뒤 전환할 시작 정각을 정한다. 이전 버전에는 전송 기록이 없으므로 이미 보낸 현재 시간대를 새 버전이 다시 보내지 않게 다음 정각을 권장한다. 배포와 점검이 끝날 여유를 둔다.
5. 첫 실행 전 `NOTIFY_START_AT`에 그 시각을 ISO UTC로 넣는다. 예를 들어 KST 2026-09-19 03:00은 `2026-09-18T18:00:00Z`다. 이 예시를 그대로 쓰지 말고 실제 전환 시각으로 바꾼다.

`NOTIFY_START_AT`은 첫 스케줄러 상태를 만들 때만 적용한다. 현재 정각보다 과거로 소급하지 않고, 비정각 값은 다음 정각으로 올린다. 생략하면 최초 실행의 현재 정각부터 시작한다. 이미 저장한 `notificationScheduler/state.firstSlot`은 환경변수 변경으로 덮어쓰지 않는다. 잘못된 형식은 점검 요청도 503으로 실패한다. 운영 중 이 상태를 삭제해 발송 기록을 초기화하지 않는다.

서버 설정을 넣은 뒤 v1.5.0을 배포하고 Vercel에서 배포 커밋을 확인한다. 이 시점에도 GitHub 예약 변수는 바꾸지 않는다. 기존 GitHub 호출도 배포된 새 API를 이용하면 같은 발송 기록과 동시 실행 제한을 공유한다.

## 2. 발송 없는 연결 점검

이전 API는 `?check=1`을 무시하고 알림을 보낼 수 있다. 따라서 Vercel에서 v1.5.0 배포 커밋을 확인하기 전에는 아래 점검 URL을 호출하지 않는다. 캐시된 앱 버전 표시만으로 판단하지 않는다.

cron-job.org에서 작업 하나를 비활성 상태로 만들고 다음 값을 넣는다.

| 항목 | 설정 |
|---|---|
| 이름 | `SASA Task Manager notifications` |
| URL | `https://<운영 도메인>/api/notify?check=1` |
| 요청 방식 | POST |
| 헤더 | `Authorization: Bearer <CRON_JOB_SECRET 값>` |
| 본문 | 비움 |
| 실행 간격 | 5분마다, 매시간 `0,5,10,15,20,25,30,35,40,45,50,55`분 |
| 시간대 | `Asia/Seoul` |
| 응답 제한시간 | 30초 기본값 유지 |
| 응답 본문과 헤더 저장 | 끔 (`saveResponses: false`) |
| 3xx 응답을 성공으로 간주 | 끔 (`redirectSuccess: false`) |
| 실패 알림 | 켬, 첫 실패부터 |
| 실패 후 복구 알림 | 켬 |
| 자동 중지 알림 | 켬 |

설정 필드와 POST 지원은 [공식 REST 문서](https://docs.cron-job.org/rest-api.html)에 있다. `redirectSuccess`는 3xx를 성공으로 볼지의 설정이며 TLS 검증 설정이 아니다. 응답 저장을 켜면 공식 FAQ 기준으로 응답 헤더와 본문이 2일 보관되므로 평소에는 끈다. 실행 기록의 시각과 상태만으로 먼저 확인한다.

콘솔에서 수동 점검을 한 번 실행한다. 예상 응답은 HTTP 200과 다음 JSON이다.

```json
{ "ok": true, "check": true, "sendsNotifications": false }
```

이 점검은 Firebase 서버 설정과 스케줄러 상태 문서 읽기를 확인한다. 과제와 기기 구독을 읽거나 상태를 쓰거나 푸시를 보내지 않는다. 실제 기기 연결과 수신은 테스트 계정의 앱 설정에서 테스트 알림으로 별도 확인한다.

## 3. 예약 경로 전환

1. 점검이 통과하면 같은 작업의 URL에서 `?check=1`을 지운다. 본문은 계속 비워 둔다. URL을 바꾼 뒤에는 실제 예약 알림을 보낼 수 있다.
2. 정한 시작 정각 전에 작업을 활성화한다. 그 이전 호출은 시작 정각 이전의 알림을 보내지 않는다. 새 예약은 현재 상태와 다음 실행 시각을 콘솔에서 확인한다.
3. 시작 정각 이후 실행 기록과 Vercel의 합계 로그를 확인한다. 테스트 계정의 iPhone PWA에서 수신 시각과 눌렀을 때의 화면 이동도 확인한다. HTTP 200이 모든 기기의 수신을 뜻하지는 않는다.
4. 새 경로가 동작하는 것을 확인한 뒤 GitHub 저장소의 **Settings → Secrets and variables → Actions → Variables**에 `NOTIFY_SCHEDULER=cron-job.org`를 등록한다. `.github/workflows/notify.yml`은 schedule 실행만 건너뛰고 수동 실행은 유지한다.

새 경로를 확인하기 전에 GitHub 워크플로를 삭제하거나 비활성화하지 않는다. 이 코드 변경은 GitHub 변수나 cron-job.org 계정을 자동 변경하지 않는다.

## 동작 범위와 장애 확인

- 서버는 현재 정각을 먼저 처리하고 90분 이내의 직전 정각을 복구한다. 이미 지난 마감 임박 알림은 보내지 않는다.
- 기기별 전송은 최초 시도 포함 총 3회까지다. 재시도 대상은 네트워크 오류, 408, 429와 5xx다. 첫 실패 뒤 최소 1분, 두 번째 실패 뒤 최소 3분을 기다리므로 5분 예약에서는 대개 다음 호출이 재시도를 맡는다.
- 처리 예산은 18초, Vercel 함수 제한은 25초, 개별 HTTPS 전송 제한은 5초다. 18초는 진행 중인 Firestore 요청을 끊는 제한이 아니다. 커서를 남겨 다음 호출에서 이어가며 응답 후 백그라운드 실행에 의존하지 않는다.
- 같은 사건의 전송 기록, 푸시 topic과 알림 tag로 중복을 억제한다. 푸시 전송 후 기록 실패가 생기면 재전송이 가능하므로 정확히 한 번 수신을 보장하지 않는다.

| 결과 | 확인할 점 |
|---|---|
| 401 | 해당 키가 Vercel과 작업 헤더에서 일치하는지 확인 |
| 405 | POST 설정 확인 |
| 503 | 서버 설정, 시작 시각 형식, Firestore 오류 또는 부분 발송 실패 확인 |
| 200, `busy: true` | 다른 실행이 있거나 30초 안에 재호출됨. 다음 예약에서 확인 |
| `pending > 0` | 다음 호출에서 이어갈 작업. 여러 호출 동안 줄지 않으면 장애 확인 |
| `failed`, `abandoned`, `userFailures > 0` | 오류와 재시도 한도 확인. 단순 재실행으로 모두 해결된다고 가정하지 않음 |
| 작업 자동 중지 | 원인을 해결한 뒤 콘솔에서 활성화하고 다음 실행 확인 |

호출은 하루 288회다. 발송할 일이 없는 호출도 제어 상태와 만료 기록 정리에 Firestore 사용량이 생긴다. 무료 운영은 각 서비스의 무료 한도 안에서 가능하며 사용자와 구독 수가 늘면 Vercel 실행량, Firestore 읽기와 쓰기, 실제 처리 시간을 확인한다.

## 기록 보관과 복구

예약 전송과 실행 기록은 해당 정각에서 48시간 뒤, 테스트 제한 기록은 마지막 시도에서 48시간 뒤에 삭제 대상이 된다. 정상 예약 실행이 `notificationDeliveries`, `notificationRuns`, `pushTestLimits` 각각 최대 40개씩 정리한다. Firestore TTL 정책은 필수가 아니다. 정리가 밀리거나 예약이 멈추면 기록이 더 오래 남을 수 있다. 상세 기록 범위는 [푸시 신뢰성](push-reliability.md)에 있다.

cron-job.org 장애가 지속되면 해당 작업을 멈추고 GitHub의 `NOTIFY_SCHEDULER` 변수를 삭제하거나 다른 값으로 바꿔 기존 시간별 호출을 복구한다. 긴급 수동 실행도 가능하지만 실제 예약 알림을 보낼 수 있다. 서버 코드를 이전 버전으로 되돌리면 중복 억제가 사라지므로, 스케줄러 복구와 코드 롤백을 구분한다. 비밀키가 노출됐다면 Vercel과 해당 작업의 키를 교체하고 재배포한다.
